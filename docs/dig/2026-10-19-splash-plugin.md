# dig log: SwiftBarからのStrata／Splash管理

## 目的・前提・制約
- LLM以外のプラグインも追加できる汎用の `swiftbar-plugins` リポジトリを作る。今回の対象はStrataとSplashの状態表示・起動停止・モデル選択。
- ログのファイル名は議論の継続性のため維持する。Q1〜Q12はSplashを前提に詰めたもので、Strata固有の設定やダウンロード動作への適用は未確認。
- このログはfork前の会話と、新ワークスペースでの引き継ぎ指示を基に開始した。
- 2026-10-19確認: リポジトリの追跡ファイルは見出しだけの `README.md`。作業ツリーはクリーン。リポジトリおよび確認した親ディレクトリに追加の `AGENTS.md` / `CLAUDE.md` はない。
- グローバル指示に従い、dig → ユーザー承認 → plan → ユーザー承認 → 実装の順で進める。設計・実装計画の承認はまだない。
- 利用環境はM6・32GB、macOS 27.0.1、Homebrew版Splash 1.3.2。ユーザーは他のアプリ用のメモリを残したく、総使用量12〜15GB程度を希望している。
- 既存Splashは親のHerdrペインで稼働中。外部プロセスとして扱い、勝手に停止・取り込みしない。モデル名・個人の起動設定はリポジトリに保存しない。
- 上記設定の短い試験では日本語約25 tok/s、コード約68〜69 tok/s。Metal確保量約9.4GiB、起動時ピーク約10.4GiB。プロセス全体のメモリは未確認で、システムのメモリ圧迫判定はwarningだった。長文・品質の評価は未完了。

## 決定事項
- Strata Menubarは変更せず、そのまま維持する。
  - 出典: fork前のユーザー発言および引き継ぎ指示。
- 新リポジトリはLLM専用にせず、様々なSwiftBarプラグインを追加できるものにする。
  - 出典: 「今後も色々追加するかも。llm関係なく」。
- SwiftBarからStrataとSplashの両方を操作できるようにする。Strata Menubarのコードは変更しない。
  - 出典: dig前の依頼、およびQ13への訂正「swiftbarからstrataの操作もできるようにする」。
- SwiftBar利用時はStrata Menubarを終了している前提とする。同時利用のための連携や設定同期は前提にしない。
  - 出典: 「swiftbar使う時はstrata menubarは終了してると思う」。
  - アプリ終了とサーバー終了は別であり、外部で起動されたサーバーを自動停止・取り込みする許可とは扱わない。
- セッションforkとワークスペース移動は完了済みで、繰り返さない。
  - 出典: 引き継ぎ指示。

- モデル選択は設定に登録した候補から選ぶ方式（Q1のA）とする。ただし、リポジトリは具体的なモデルを知る必要はなく、モデル一覧を組み込まない。
  - 出典: Q1への回答。登録モデル選択を承認し、特定モデルをリポジトリに組み込まないよう指定。
  - モデル一覧の保存先・スキーマは未決。
- モデル一覧はローカル設定ファイルを直接編集する方式（Q2のA）とする。メニューから設定ファイルを開けるようにする。
  - 出典: Q2への回答「Aだが、jsonにはモデルのダウンロード場所も書かないとなのでは」。
- Splash公式仕様を確認: モデルIDで起動し、重みとドラフトはHugging Faceキャッシュで管理する。既定の保存先は `~/.cache/huggingface/hub`。`HF_HUB_CACHE`でダウンロードキャッシュを変更できるが、既存ダウンロードは移動しない。Splashのデータディレクトリにはキャッシュへのリンク等が残る。
  - 出典: https://github.com/incoai/splash/blob/main/DEVELOPMENT.md#model-cache
  - 設計上の含意: 各モデルのGGUFファイルパスをプラグインが管理する必要はない。キャッシュ保存先の設定はQ3で合意済み。

- モデルのダウンロード先は、省略可能な共通設定 `modelCacheDir` で指定できるようにする。指定時は `HF_HUB_CACHE` としてSplashへ渡し、省略時は保存先を上書きしない。既存モデルの移動は行わない。
  - 出典: Q3への回答「a」。

- モデルごとの起動設定は `args` にSplashのCLI引数配列として記述する。引数はシェル文字列として評価せず渡す。モデルID・ホスト・ポートなどプラグインが管理する項目の重複指定は禁止する。
  - 出典: Q4への回答「a」。

- プラグイン管理下のサーバー稼働中に別のモデルを選ぶ場合、確認ダイアログを出し、承認後に停止・再起動して切り替える。確認では生成中のリクエストが中断されることを伝える。外部起動のサーバーは停止・切り替えの対象にしない。
  - 出典: Q5への回答「b」。

- 通常のStartおよびモデル切り替え後の起動は `--offline` で行う。取得・更新は別メニュー「ダウンロード／更新して起動」から、確認後にオンライン起動してSplashに任せる。プラグイン独自のダウンロード処理は作らない。
  - 出典: Q6への回答「b」。

- SwiftBarを終了してもSplashは動作を継続する。SwiftBar再起動後は、プラグイン自身が起動した同一サーバーについて表示・操作を再開できるようにする。外部サーバーの取り込みとは区別し、停止は明示的なStopで行う。
  - 出典: Q7への回答「a」。

- プラグインによる起動は明示的な操作のみとする。Mac再起動・ログイン時の自動起動や、Splashサーバープロセス終了後の自動再起動は行わない。Splash自身の内部エンジン復旧機能は変更しない。
  - 出典: Q8への回答「a」。

- メニューバーの常時表示はアイコンのみとする。稼働・停止・起動中・エラーを形やマークでも区別し、色だけに依存しない。モデル名などの詳細はメニュー内に表示する。
  - 出典: Q9への回答「a」。

- 開いたメニューには、状態・モデル名・接続先、Start／Stop・モデル選択・取得／更新・チャット／ログ／設定への導線に加え、生成速度・メモリ使用量・コンテキスト上限を表示する。取得／更新はSplashのみ。
  - 出典: Q10への回答「b」、Q17。
- メモリ表示はMetal割り当て量ではなく、Macのアクティビティモニタの「メモリ」列に相当する値を求める。RSSやシステム全体のRAM使用量で代用しない。OS由来のphysical footprintを取得候補とし、取得方法・権限・単位を確認してアクティビティモニタと実測比較する。現時点では取得方式も一致も未検証。
  - 出典: Q19への回答「Macのアクティビティモニタで見たときと同じメモリ使用量が表示されてて欲しい」。

- 管理するSplashサーバーは同時に1つとし、全モデルで共通のポートを使う。モデル選択で切り替え、複数モデルの同時起動は扱わない。設定ポートに外部Splashがある場合は外部稼働として表示し、起動・停止・切り替えは行わない。
  - 出典: Q11への回答「a」。

- Stopは処理状態にかかわらず毎回確認する。
  - 理由: 処理中かどうかによる条件分岐を避け、動作をシンプルにする。
  - 出典: Q12への回答「aでいいんじゃない？シンプルで」。

- StrataとSplashは1つのメニューバーアイコン・メニューにまとめ、それぞれの状態・起動停止・モデル選択を操作する。LLM以外のプラグインは独立して追加できる構成にする。
  - 出典: Q14への回答「a」。

- StrataとSplashは独立して起動・停止でき、同時稼働も許可する。もう一方の稼働による起動制限や自動停止・切り替えは設けない。メモリ使用量を踏まえた起動・停止はユーザーが判断する。
  - 理由: エンジン間の連動を加えず、シンプルにする。
  - 出典: Q15への回答「b。変に複雑にしない。ユーザーの自己責任で停止起動する」。

- Strataのモデル一覧は表示名と既存の設定JSONのパスを登録する方式とする。expert cache・コンテキストなどのモデル／エンジン設定は参照先JSONで管理し、SwiftBar側に上書き項目を持たせない。Strata Menubarの保存設定とは同期しない。
  - 出典: Q16への回答「a」。
  - 起動先のホスト・ポート等、プラグインの接続管理に必要な項目は別途起動契約を確認する。

- Strataは準備済みモデルの起動・停止・選択のみを扱う。モデルの取得・初回準備はStrataのセットアップやStrata Menubarで行い、SwiftBarからは実行しない。Splashの「ダウンロード／更新して起動」は維持する。
  - 出典: Q17への回答「a」。

- サーバー操作の共通ルールをStrataにも適用する。各エンジン内は1サーバー、Stopは毎回確認、稼働中のモデル変更は確認後に停止・再起動する。SwiftBar終了後も継続し、再起動後は自己起動した同一サーバーの管理を再開する。ログイン時の自動起動・異常終了後の自動再起動は行わず、外部サーバーは表示のみで停止・取り込みしない。StrataとSplashの同時稼働は許可する。
  - 出典: Q18への回答「a」。

- メモリ表示の対象は推論エンジン単体とし、APIサーバーやその他の関連プロセスは合算しない。アクティビティモニタの該当エンジンプロセスの「メモリ」列と照合する。
  - 出典: Q20への回答「それはbでいいです」。

## 未決・保留
- Q13は対象範囲の誤りにより未承認。両エンジンを含むQ19で設計の最終確認を行う。以下は補足案として承認待ち。
  - 設定は `~/.config/swiftbar-plugins/llm.json` の1ファイルに `strata` と `splash` の設定を分けて記載する。選択モデルや所有権情報は設定とは別のユーザー領域に保存する。
  - 接続先は両方 `127.0.0.1` 限定。ポートはエンジンごとに設定可能で既定はStrata 8080、Splash 8000。同じポートの指定は設定エラーとする。
  - 状態は5秒ごとに更新する。Splashの速度は直近の観測区間の出力トークン増分／経過時間、StrataはAPIが返す移動窓の生成速度を使い、累積平均とは区別する。生成していないときや有効な観測がないときは `—` と表示する。
  - 取得できない監視値は `—` とする。メモリはOSから取得し、アクティビティモニタの指標に合わせる。対象はQ20で合意した推論エンジン単体とする。
  - 未取得モデルの通常起動はエラーと取得操作への案内を表示し、自動でオンライン起動へ切り替えない。
  - モデル切り替え・取得／更新の確認には、必要な停止と処理中断も含める。キャンセル時は選択も稼働状態も変えない。停止失敗時は次の起動を行わない。
  - `plugins/` をSwiftBarのプラグインフォルダとして指定する。補助コードや設定例はその外に配置する。リポジトリには空のモデル一覧の設定例だけを置く。

  - スクリプトの実行環境、SwiftBarの更新・クリック操作と切り離したサーバー管理、確認ダイアログの実装、ログと状態の保存先。
  - SwiftBarへの導入方法。`/Applications/SwiftBar.app` には見つからなかったため、他の配置を含む導入状況を確認する。
